# M.4 Scope Proposal

**Status:** proposal for founder approval — nothing here is approved, scheduled or implemented. This document does not create the M.4 Kiro specification.
**Basis:** [M4_ARCHITECTURE_AUDIT.md](M4_ARCHITECTURE_AUDIT.md), [M4_GAP_ANALYSIS.md](M4_GAP_ANALYSIS.md), [M4_PRIVACY_SECURITY_REVIEW.md](M4_PRIVACY_SECURITY_REVIEW.md).
**Design constraint:** M.4 is **incremental**. The existing idempotency layer, the HTTP contract, the data model and the reporting journeys stay as they are. M.4 adds durability around them; it does not replace them.

---

## 1. Design stance

1. **Preserve idempotency, do not replace it.** The server-side contract (`Idempotency-Key` header, SHA-256 payload fingerprint, 409 on conflict, replay returns the original) is proven and tested in both storage modes (`apps/backend/tests/test_idempotency.py`, `apps/backend/tests/test_store_postgres.py`). M.4 must not change `apps/backend/store.py`, `apps/backend/store_pg.py` or the `POST /api/reports` semantics.
2. **The only client change is durability.** The key is generated by the same `newSubmissionKey()` / `newIdempotencyKey()` functions that exist today (`apps/frontend/src/lib/api.ts:39-43`; `apps/mobile/lib/api/report_api.dart:131-138`). The change is *where the key lives*, not how it is computed or checked.
3. **Automatic offline submission is not required.** Nothing below depends on the app transmitting a report on its own. The user always chooses to send. This is a deliberate product choice, not an omission — see §5.
4. **Every new persistent store is a privacy liability.** Any store M.4 introduces must be treated as if it held the incident text (which it does), because the safety promise in the app is that this data is transient.
5. **Nothing in P0 changes the reporting flow or the schema of `reports`.** One P1 item (admin identity and audit) is expected to add tables; everything else in P0 can ship without a migration.

## 2. P0 requirements — required before any real report is collected

Ordered by dependency. Each is independently shippable and independently testable.

### P0-1. Retention, deletion and key expiry
**Closes:** G-01, G-15 · **Risk:** R-01
- A written, founder-approved retention policy: retention period for open reports, for closed reports, and for idempotency keys.
- An automated deletion path (a scheduled script or service) that deletes reports past their retention period and idempotency keys past theirs. The `created_at` columns already exist on both tables (`apps/backend/migrations/001_init.sql:17`, `:27`), so expiry is a `DELETE ... WHERE created_at < now() - interval`.
- Deletion must also remove or tombstone the corresponding idempotency key deliberately, rather than relying on `ON DELETE CASCADE` (`apps/backend/migrations/001_init.sql:26`) — today a deleted report's key disappears silently, and a late retry then creates a *new* report.
- A deletion audit record: count, window and operator for every run.
- Retention of database backups specified separately from the live database.
- A documented, operator-facing deletion procedure that a non-engineer can run.

### P0-2. Admin identity and audit logging
**Closes:** G-02, G-11 · **Risk:** R-02
- Per-user admin authentication replacing the shared `X-Admin-Key` (`apps/backend/reports.py:14-29`). Interim acceptable form: named operator accounts with individual credentials and per-account rate limiting, so a credential can be revoked without rotating a shared secret.
- Role separation: at minimum *read reports* and *change status*.
- An append-only audit log of every admin action — who, when, which report, which action, from which address — written to a table no admin can edit through the API.
- `GET /api/reports` scoped and paginated so a responder sees what their role permits (`apps/backend/reports.py:61-63`).
- This is the one P0 item expected to require a schema migration (admin accounts, sessions, audit log).

### P0-3. Production deployment and transport security
**Closes:** G-03, G-04, G-16 (partly) · **Risk:** R-03
- Backend behind a TLS-terminating reverse proxy; a single Uvicorn worker (`apps/backend/DATABASE.md:39-41`).
- Proxy overwrites `X-Forwarded-For`; Uvicorn trusts only that proxy, so `request.client.host` is the real client (`apps/backend/ratelimit.py:5-8`).
- Production CORS allowlist replacing the hard-coded `http://localhost:5173` (`apps/backend/main.py:55`).
- Security response headers: HSTS, `X-Content-Type-Options`, `Referrer-Policy`, a restrictive CSP, `frame-ancestors`.
- Rate limiting that survives restarts, or an explicit, documented decision to run one worker and accept the limitation.
- Process supervision, health monitoring against `/health/ready` (`apps/backend/main.py:25-29`), log hygiene and log retention.
- Secret management and rotation for `SAFESIGNAL_ADMIN_KEY` and `DATABASE_URL`.

### P0-4. Storage durability under continuous test
**Closes:** G-06, G-13, G-12 (partly) · **Risk:** none directly, but it gates everything else
- A PostgreSQL service container in CI so `apps/backend/tests/test_store_postgres.py` stops self-skipping (`.github/workflows/ci.yml`).
- A Flutter job in CI running `flutter analyze` and `flutter test`.
- A frontend test harness — currently `apps/frontend/package.json:6-11` has no test runner — with at least the submission path covered.
- The web build served with `VITE_PROTOTYPE=false` verified in the deployment, so the mock dashboard is not reachable in production (`apps/frontend/src/lib/prototype.ts:1-6`).

### P0-5. Durable client submission identity
**Closes:** G-05 · **Risk:** R-01 (duplicate reports undermine trust in the whole system)
- Persist the idempotency key **together with the exact payload it was issued for**, in app-private storage, with a short expiry, deleted on success, on reset and on Quick Exit.
- On restart, the client reuses the stored key for the stored payload, so an unknown-outcome submission resolves to the original report instead of creating a duplicate.
- No new server endpoint, no schema change, no change to the key format or to the fingerprint rules.

### P0-6. Privacy notice, consent and legal basis
**Closes:** G-07, G-14 · **Risk:** R-04 (partly)
- A published privacy notice that states what is collected, what is not, where it is stored, who can see it, how long it is kept and how to ask for deletion.
- `consentToShare` captured for real, or removed from the interface and the schema so the field stops implying a control that does not exist (`apps/backend/migrations/001_init.sql:14`; `apps/frontend/src/lib/api.ts:34`; `apps/mobile/lib/api/report_api.dart:73`).
- Legal review under Kenya's Data Protection Act (`docs/SECURITY.md:29`).

### P0-7. Quick Exit hardening on Android
**Closes:** G-09 · **Risk:** R-05
- `FLAG_SECURE` on the reporting and review activities, so the recent-apps thumbnail and screenshots are blocked (`apps/mobile/lib/screens/review_screen.dart:53-62` shows the sensitive text).
- `android:allowBackup="false"` or an explicit backup-exclusion rule, so nothing leaves the device.
- Clipboard reference code cleared on exit or after a short delay (`apps/mobile/lib/screens/confirmation_screen.dart:79-86`).
- User-facing copy that states exactly what Quick Exit erases and what it cannot (`apps/mobile/lib/widgets/quick_exit_button.dart:9-10`).

## 3. P1 requirements — required before a supervised pilot

### P1-1. Durable local draft (see §5 for the option analysis)
**Closes:** G-08 · **Risk:** R-05 (partly)
- One pending draft, persisted in app-private encrypted storage, with a short TTL, restored on next launch with the user's explicit confirmation, and deleted on success, reset or Quick Exit.
- Mobile first; web parity decided separately (see §7).

### P1-2. Operator tooling and runbook
- A real admin experience: real data, scoped access, status changes written through the audited endpoint, and a runbook for the person on duty.
- Reference-code lookup, implemented as a **bearer-token** flow with rate limiting and audit, or explicitly deferred (see §7).

### P1-3. Metadata minimisation
**Closes:** R-04
- Decide the precision the response team actually needs from `created_at`; expose bucketed or rounded timestamps for analysis while keeping the exact value only where operationally necessary.
- Restrict plate and SACCO to internal-only fields with narrower access than route and area.
- Add guidance in the details screen: do not type names, phone numbers or exact addresses into the free-text fields.

### P1-4. Verification closure
**Closes:** U-01 … U-08, U-14
- Verify PostgreSQL on the target server version.
- Execute and record a backup and a restore on the real server.
- Create and verify least-privilege roles.
- Manual browser and screen-reader pass of the web journey; device test of the mobile journey against PostgreSQL storage (`docs/CHECKLIST.md:19-20`, `:92`).
- Independent review of the Kiswahili safety wording (`docs/CHECKLIST.md:79`).

### P1-5. Abuse and availability controls
- CAPTCHA or a challenge on the public submission path, or a documented decision not to use one.
- Rate limiting on the assistant and health routes; a persistent limiter once more than one worker is contemplated.
- A published vulnerability contact (`docs/SECURITY.md:33`).

## 5. Offline architecture options

The question is not "how do we submit offline" but "what happens to a report the user has written when the connection is unreliable, the app is killed, or the outcome is unknown".

### Option A — No durable client storage (status quo, with clearer failure messaging)
Keep every draft in memory, exactly as today (`apps/mobile/lib/models/report_draft.dart:1-3`; `apps/frontend/src/App.tsx:12`). Improve only the copy and the flow after a failed submission: state plainly that the report has **not** been sent, keep the screen open, and tell the user that tapping again is safe because the same submission key is reused (`apps/frontend/src/screens/NextStepScreen.tsx:173`).
- **Pros:** no new attack surface, no new dependency, no new privacy statement required, no new deletion problem. The retry semantics are already proven by the timeout integration test (`apps/mobile/test/integration/backend_timeout_retry_test.dart:86-113`).
- **Cons:** a killed app, a killed browser tab or a forced restart loses the report. The unknown-outcome case cannot be reconciled after a restart.
- **Cost:** lowest.

### Option B — Durable single draft with a durable key (recommended)
Persist exactly one pending report — the payload **and** the idempotency key issued for it — in app-private encrypted storage with a short TTL. On launch, offer to restore it. The user sends it, or retries it, when they choose.
- **Pros:** closes G-05 and G-08 with one mechanism. Reuses the existing key generation and the existing server contract; no new endpoint, no schema change, no change to fingerprinting. A restored draft retries with the same key, so an unknown outcome resolves to the original report instead of duplicating it.
- **Cons:** introduces the first place where incident text exists on the device. Requires an encryption key strategy, a TTL, an explicit restore prompt, and deletion on success/reset/Quick Exit.
- **Cost:** medium.

### Option C — Durable outbox with automatic submission on reconnect
A queue of pending reports, each with its own key, flushed by a background task when connectivity returns.
- **Pros:** the user never has to think about connectivity again.
- **Cons:** the largest privacy surface (a queue of incident text at rest), the most failure modes (partial flush, key expiry, ordering, duplicate risk across restarts), and it needs Android background execution. Critically, it makes the app transmit data at a moment the user did not choose, which is in tension with the app's "the user decides when to send" model and with the Quick Exit promise. It also complicates the Quick Exit guarantee: "exit now" would have to mean "erase the queue", losing unsent reports — or mean "keep it", which contradicts the current meaning.
- **Cost:** high.

### Option D — Browser `localStorage` / `sessionStorage` drafts (web)
Rejected. `localStorage` is plaintext, survives restarts, is readable by any script on the origin and by any browser extension, is included in profile sync and disk backups, and has no encryption story. The current web design keeps everything out of browser storage for exactly this reason (`apps/frontend/src/App.tsx:12`); only the theme preference is stored (`apps/frontend/src/lib/theme.ts:3`). `sessionStorage` reduces exposure but still persists to disk while the tab is open and is lost on reload — it buys little over Option A.

### Recommendation

**Option B for the mobile client, Option A for the web client, in that order of priority.**

Rationale: the mobile app is the client in the field, where connectivity loss, battery death and app switching are routine; the web app is used in a browser where a reload is a normal user action and where the storage surface is worse. Option B delivers the two things that matter most — the report is not lost, and a retry cannot create a duplicate — while keeping the proven retry semantics intact.

**Automatic offline submission is not recommended for M.4.** Nothing in the P0 or P1 requirements needs it, Option B does not need it, and it is the one change that would most increase the blast radius of a device compromise. It can be reconsidered after a pilot, with evidence, if users demonstrably fail to resubmit.

## 8. Acceptance criteria candidates

Written so that each is verifiable by an automated test, a documented manual procedure, or an artifact on disk. These are candidates for the M.4 specification, not approved criteria.

### Reliability and idempotency (preserving existing behaviour)
- **AC-1** — A retry of an unchanged submission with the same key returns the original reference code and creates no second report, in PostgreSQL mode. *(already covered by `apps/backend/tests/test_store_postgres.py:50-56`; must keep passing)*
- **AC-2** — 16 concurrent submissions with the same key produce exactly one stored report. *(already covered by `apps/backend/tests/test_store_postgres.py:58-61`)*
- **AC-3** — A key reused with a different payload returns 409 and leaves the stored report unchanged. *(already covered by `apps/backend/tests/test_idempotency.py:36-41`)*
- **AC-4** — A replay consumes no rate-limit allowance. *(already covered by `apps/backend/tests/test_store_postgres.py:64-68`)*
- **AC-5 (new)** — The PostgreSQL integration suite runs in CI on every push and is never skipped. Verified by CI log inspection, not by a local run.
- **AC-6 (new)** — After the mobile app is killed and relaunched, a pending draft is offered for restore and, when resubmitted unchanged, produces no second report and returns the original code.
- **AC-7 (new)** — After a network timeout with the server later accepting the request, the unchanged retry still yields exactly one stored report. *(extends the existing opt-in integration test to the restart case)*

### Privacy and retention
- **AC-8 (new)** — A report older than its retention period is deleted by the automated job, and the job logs the count, the window and the operator.
- **AC-9 (new)** — Idempotency keys older than the key retention period are deleted, and the report they referenced is unaffected.
- **AC-10 (new)** — Deleting a report does not silently allow a later retry with the same key to recreate it; the outcome is either a documented replay or a documented new report.
- **AC-11 (new)** — Every admin list and status change appears in the audit log with actor, timestamp, target and action; an admin cannot modify or delete audit entries through the API.
- **AC-12 (new)** — A restored local draft exists only in app-private storage, is encrypted at rest, is deleted on Quick Exit, and does not appear in an `adb backup` of the device.
- **AC-13 (new)** — No report content, phone number, plate or location appears in any application log, crash report or analytics output.

### Quick Exit and device hygiene
- **AC-14 (new)** — With the report screen showing route and plate, a screenshot on a physical device produces a black or blocked frame.
- **AC-15 (new)** — The recent-apps thumbnail shows no report content after leaving the reporting screens.
- **AC-16 (new)** — The app's data directory contains no report text after Quick Exit, verified by inspecting app-private storage on a device.

### Deployment
- **AC-17 (new)** — The API is reachable only over TLS; a plain-HTTP request to the public host is refused or redirected.
- **AC-18 (new)** — `X-Forwarded-For` supplied by a client is not used for client identity; the limiter sees the real client address.
- **AC-19 (new)** — The production build serves the API with the production CORS origin only; a request with a foreign `Origin` header receives no CORS grant.
- **AC-20 (new)** — Responses carry HSTS, `X-Content-Type-Options`, `Referrer-Policy` and a CSP with `frame-ancestors`.
- **AC-21 (new)** — A backup is taken, restored into a clean database, and the restore is verified by counting rows; the result is recorded in the runbook.

### Quality gates
- **AC-22 (new)** — `flutter analyze` and `flutter test` run in CI on every push.
- **AC-23 (new)** — The web submission path has an automated test covering the same-key retry case.
- **AC-24 (new)** — `ruff check .` and `pytest -q` remain clean with the PostgreSQL service attached.

## 9. Suggested delivery sequence

Each increment is independently shippable, preserves the existing idempotency design, and can be stopped at any point without leaving the product in a worse state.

| # | Increment | Contents | Gate |
|---|---|---|---|
| I-1 | Test foundations | PostgreSQL in CI, Flutter in CI, frontend test harness | AC-5, AC-22, AC-23, AC-24 |
| I-2 | Retention and deletion | Policy, deletion job, key expiry, deletion audit, runbook | AC-8, AC-9, AC-10 |
| I-3 | Admin identity and audit | Named accounts, roles, audit log, scoped and paginated list | AC-11 |
| I-4 | Deployment | TLS, proxy, CORS, headers, supervision, monitoring, secret rotation | AC-17 … AC-21 |
| I-5 | Quick Exit hardening | `FLAG_SECURE`, backup exclusion, clipboard clearing, honest copy | AC-14, AC-15, AC-16 |
| I-6 | Durable client identity | Persisted key + payload, no new server contract | AC-6, AC-7 |
| I-7 | Durable draft (Option B) | Encrypted single draft, restore prompt, deletion lifecycle | AC-12 |
| I-8 | Privacy notice, consent, legal | Notice, consent decision, legal review | AC-13 |
| I-9 | Verification closure | Device, browser, backup/restore, Kiswahili review, independent review | AC-21 and the P1-4 list |

I-1 and I-2 have no dependency on a decision; I-3 and I-4 are gated on D-02 and D-05; I-6 and I-7 are gated on D-03 and D-10; I-8 is gated on D-04 and D-08.

**What "done" for M.4 means:** every P0 acceptance criterion passes, the pilot decision in D-06 can be taken with the evidence in hand, and no P0 item is described in the user interface as more protective than it is.
